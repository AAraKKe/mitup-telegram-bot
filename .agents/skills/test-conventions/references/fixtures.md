# Fixtures and Test Data

## Fixture dependency graph

```
app                     → Application (session-independent)
tg_chat                 → Chat (session-scoped, id=123)
tg_user                 → User (adapts to user_with_settings if in scope)
tg_message              → Message (depends on tg_user, tg_chat)
tg_callback_query       → CallbackQuery (depends on tg_user, tg_message)
update                  → Update (depends on all tg_* fixtures; supports indirect parametrize via UpdateRequest)
context                 → StubMitupContext (depends on app, update; builds via build_context)
handler_context         → HandlerContext (bundles update + app for call_handler's second overload)
conversation            → ConversationTester (depends on app, tg_user, tg_chat)

user                    → UserModel (id=1, tg_user_id=123, 2 meetups)
settings                → Settings (id=1, timezone=Europe/Madrid; depends on user)
user_with_settings      → UserModel (id=1, tg_user_id=123, 2 meetups, settings with lang param)
meeting                 → Meetup (id=123, owned by user_with_settings)

lang                    → str (generated by pytest_generate_tests; default "en", see below)
mock_session            → MockDbSession (patches mitup_bot.db.sessionmaker)
db_config               → DbConfig (session-scoped, dummy values)
configure_test_metrics  → auto, session-scoped (configures STDOUT metrics)
test_env                → auto, session-scoped (sets TEST_* env vars)
```

## Language testing

Tests default to English (`--lang en`). The `lang` fixture is injected by `pytest_generate_tests` in the root `conftest.py` — any test that includes `lang` in its fixture names gets parametrized with the selected language.

The `user_with_settings` fixture consumes `lang` and sets `settings.language = lang`, so all handler tests that use `user_with_settings` are automatically language-aware.

### Running tests with different languages

```bash
# Default: English only
uv run mb test tests/path/to/test_file.py

# Specific language
uv run mb test tests/path/to/test_file.py --lang es

# All supported languages (parametrizes each test per language)
uv run mb test tests/path/to/test_file.py --lang all
```

When writing tests that assert on user-facing text (views, messages, button labels), always derive the expected text from the user's language rather than hardcoding English:

```python
# Good — works for any language
expected_view = factory.main_menu_view(lang=user_with_settings.lang)
message = MeetingMessages.DELETE_MEETING.get(lang=user_with_settings.lang)

# Bad — breaks when --lang es
expected_view = factory.main_menu_view(lang="en")
```

If a test does NOT need language parametrization (e.g., model logic, utilities), simply don't request the `lang` fixture or `user_with_settings` — use the plain `user` fixture instead.

## UpdateRequest — indirect parametrize for updates

`UpdateRequest` is a dataclass that configures what kind of Telegram `Update` to build. Pass it as an indirect parameter to the `update` fixture:

```python
@pytest.mark.parametrize("update", [UpdateRequest(callback_query=cb.SHOW_MEETING.with_id(1))], indirect=True)
async def test_something(update: Update, ...):
    ...
```

## Factory helpers

Never instantiate models directly. Always use these from `tests.helpers`:

| Factory | Purpose |
|---|---|
| `create_user(id, tg_user_id=123, ...)` | Creates a `User` model |
| `create_meetup(id, title="Default title", ...)` | Creates a `Meetup` model |
| `create_settings(id=1, ...)` | Creates a `Settings` model |
| `create_joined_link(user, meetup, ...)` | Creates a `JoinedUsers` link |
| `create_message(id=1, ...)` | Creates a `MeetupMessage` (DB message record) |
| `create_broadcast(id=None, ...)` | Creates a `Broadcast` model |
| `create_bot_config(admin_tg_ids)` | Creates a `BotConfig` |
| `owner_with_meeting(meeting_id=1)` | Shortcut: returns `(user, meeting)` pair |
| `telegram_user_from_user(user)` | Converts a `User` model to a Telegram `TgUser` |

### All model-generation helpers live in `tests/helpers/fixtures.py`

Every helper that builds a model (or config) instance MUST live in `tests/helpers/fixtures.py` as a
`create_*` factory and be exported from `tests.helpers`. This is a hard rule: do **not** define a
local `def draft(...) -> Broadcast` / `def make_broadcast(...)` builder inside a test module, and do
**not** wrap a centralized factory in a thin local alias. Centralizing them keeps a single source of
truth for model construction instead of re-declaring the same builder in every test file.

When a test needs a model the factories don't cover, add a new `create_*` factory (with sensible,
model-aligned defaults) to `fixtures.py`, export it via `tests/helpers/__init__.py`, then call it
from the test — never build the model inline in a reusable helper.

Mock-session or app *plumbing* helpers (e.g. one that stubs `session.get` or seeds a query result)
are **not** model factories — they may stay local to the test module, or become fixtures (see below).

### Never import functions from `conftest.py`

Test modules must never `from .conftest import ...` (or import any callable defined in a `conftest`).
`conftest.py` is for fixtures pytest injects automatically, not a helper module to import from. When
shared setup logic takes runtime arguments (so it can't be a plain autouse fixture), expose it as a
**factory fixture** that returns a callable, and type the callable with a `Protocol` (define the
Protocol in `tests/helpers/types.py` and import it under `TYPE_CHECKING`):

```python
# tests/helpers/types.py
class RegisterMember(Protocol):
    def __call__(self, user: User) -> None: ...

# conftest.py — factory fixture, injected not imported
@pytest.fixture
def register_member(mock_session: MockDbSession) -> RegisterMember:
    def register(user: User) -> None:
        mock_session.add_objects_with_statement(select(User).where(...), (user,))
    return register

# test module — inject the fixture, annotate with the Protocol
if TYPE_CHECKING:
    from tests.helpers.types import RegisterMember

async def test_x(register_member: RegisterMember, user_with_settings: User):
    register_member(user_with_settings)
```

### Relationship trap

Never pass `owner=user` to `create_meetup` when the user already exists — SQLModel `back_populates` adds the meeting to `user.meetups`, AND `create_meetup` explicitly appends it, causing duplicates.

Correct pattern:
```python
m1 = create_meetup(10, "Meeting A")
user = create_user(id=1, tg_user_id=123, owned_meetings=[m1])
```

## MockDbSession

`MockDbSession` (from `tests.helpers.stub_db`) mocks `sqlmodel.Session`. Use the `mock_session` fixture.

### Seeding data

```python
# Register by primary key (default field is "id")
mock_session.add_object(meeting)

# Register by a different field
mock_session.add_object(user, "tg_user_id")

# Shortcut for users (uses tg_user_id)
mock_session.add_user(user)

# Register multiple objects for a custom query
mock_session.add_objects_with_statement(select(Meetup).where(...), (m1, m2))
```

### Assertion methods

| Method | Checks |
|---|---|
| `assert_added(*objs)` | Objects were `session.add()`-ed |
| `assert_not_added()` | Nothing was added |
| `assert_deleted(*objs)` | Objects were deleted |
| `assert_not_deleted()` | Nothing was deleted |
| `assert_flushed()` | Session was flushed |
| `assert_not_flushed()` | Session was not flushed |
| `assert_refresh(*objs)` | Objects were refreshed |
| `assert_object_added(obj)` | Specific object was added (checks `objects_added` list) |

### Properties

- `queries_executed` — list of SQL query strings that were passed to `session.exec()`
- `objects_added` — list of objects passed to `session.add()`

## Identity matching

The `update` fixture defaults to `tg_user_id=123`. When creating users that should match the update sender:

```python
user = create_user(id=1, tg_user_id=123)
```

Use the `user_with_settings` fixture for a fully-prepped user with settings and language support (requires the `lang` fixture from `pytest_generate_tests`).
